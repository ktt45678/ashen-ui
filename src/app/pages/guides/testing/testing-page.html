Testing

ashen-ui/testing ships component harnesses, so your tests drive Ashen components the way a user does instead of reaching into markup they do not own.

Why

A test that queries .sn-select-trigger turns this library's internals into API it can never change. It also has to know that the panel renders in the overlay container, that the option list is elsewhere in the DOM, and when to call detectChanges. None of that is your application's business.

Setup

Provide provideSnAnimations('disabled'). Overlays and toasts detach when their exit animation ends. The harnesses wait for the real state either way, so a test is correct without it; it is just slower, by the length of every animation it triggers.

Harnesses work under zoneless change detection. Every read stabilizes the fixture first, so a state change made outside the harness needs no detectChanges():

Finding things

{{ codeFilters }}

Filters match on what a user perceives, a label or the visible text, not on structure. A filter that matches nothing throws with the value it looked for, so a renamed option fails loudly rather than silently doing nothing.

Keyboard

Components where selection follows focus expose sendKey(), taking the CDK's TestKey. It goes through the CDK's own key dispatch, which sets the properties a component reads; a hand-built KeyboardEvent does not.

Text getters exclude icons. A Material Symbols glyph is drawn from a ligature, so its own text is the icon's name: a selected option's raw textContent reads "Englishcheck". What a harness returns is the label.

Playwright

These are TestBed harnesses. The CDK ships no Playwright environment, so end-to-end tests still use locators. Prefer role and label selectors there for the same reason harnesses exist here: getByRole('option', { name: 'English' }) survives a markup change that .sn-listbox-option:nth-child(2) does not.
