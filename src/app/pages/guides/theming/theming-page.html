Theming

Ashen UI uses a two-tier CSS custom property system to keep every visual value customizable without selectors into component internals.

Two tiers of tokens

Tier 1 - global tokens (ashen-ui/styles/index.css) define every color, radius, spacing value, and typography size. The library ships two variants: light (:root) and dark ([data-theme="dark"]). Glass ([data-theme="glass"]) is a theme of this documentation app, built on the same contract, a worked example of the section below rather than part of the package.

Tier 2 - component tokens are declared by each component class and default to the relevant global tokens. They are the only values the component's CSS rules consume, and they are settable on the element that carries them:

/* every card */
sn-card {
  --sn-card-bg: var(--sn-color-primary-soft);
}

/* the cards in one section */
.summary sn-card {
  --sn-card-bg: var(--sn-color-primary-soft);
}

That reaches any element your own template renders, including the host of a component you use. It does not reach inside that component: Angular's emulated encapsulation scopes your stylesheet to your own elements, so a rule naming an inner class such as .sn-form-field-label never matches from a component stylesheet. For a token declared on an inner part, use snStyle, which sets it on the part directly and needs no CSS at all:

<sn-label required [snStyle]="{
  root: { '--sn-form-field-label-color': 'var(--sn-color-primary)' },
  requiredIndicator: { '--sn-form-field-required-color': 'var(--sn-color-warning)' },
}">Email</sn-label>

A global stylesheet (styles.css) is unencapsulated, so there a selector naming the inner class does work. Both are supported; snStyle keeps the change next to the markup it applies to.

The two tiers differ in reach, and picking the right one is the whole technique. A tier-1 token inherits, so setting one on a container restyles everything below it, including components that carry a variant class. A tier-2 token is declared on its element, so it is set on that element and does not inherit from a wrapper around it.

/* a danger zone: tier 1, so every control inside follows, variants included */
.danger-zone {
  --sn-color-primary-solid: var(--sn-color-error-solid);
  --sn-color-primary-solid-hover: var(--sn-color-error-solid-hover);
}

Setting a tier-2 token on a wrapper has no effect: the component declares that token on itself, and a declaration on the element always beats a value inherited from an ancestor. Name the element (.danger-zone sn-button), pass snStyle, or reach for the tier-1 token the component reads.

Either way you are setting variables, never fighting the library's own rules, so there is no ::ng-deep, no !important, and no view encapsulation fights. The library ships inside @layer components, so ordinary unlayered app CSS wins on the element without needing extra specificity.

Theme switching

Set data-theme on document.documentElement at runtime. Removing the attribute reverts to light (the :root definition). 

// switch to dark
document.documentElement.setAttribute('data-theme', 'dark');

// switch to glass
document.documentElement.setAttribute('data-theme', 'glass');

// back to light
document.documentElement.removeAttribute('data-theme');

The theme switcher in this documentation app does exactly this and persists the selection to localStorage. You can inspect the source at src/app/core/theme.service.ts.

Writing a theme: the contract

A theme is a [data-theme='name'] block that overrides the global colour tokens. The catch is what happens when you miss one: it does not fall back to something neutral, it inherits the value from :root, which is the light theme. A dark theme missing --sn-menu-bg gets a white menu, and nothing reports it.

So the required set is enforced rather than documented. theme:check, already part of test:lib, holds every theme to the same contract: 

pnpm theme:check

theme contract satisfied (78 tokens, 2 theme(s) checked).

The contract is derived, not hand-maintained: it is exactly the set of tokens the built-in dark theme overrides, so it cannot drift from the library. To start a theme, copy ashen-ui/styles/themes/_template.css, which is generated from that same set, lists every required token, and shows the dark value beside each one as a reference. Rename the selector, fill in the values, and put the file where the validator can see it.

This is not theoretical. The first run against the glass theme on this site found 24 missing tokens: the message panels, the scrollbar, and the dialog, drawer and menu backgrounds were all rendering light-theme values on a dark canvas.

Keeping a theme current

A theme written against one version drifts from the next: a token gets renamed, the contract grows, or a value sits in a block that cannot reach the element it belongs to. None of that reports itself, because CSS has no error for a custom property nobody reads. 

ng generate ashen-ui:theme-sync src/styles/my-theme.css

Remove 1 token(s) the library no longer defines:
  line 145  --sn-input-border  (did you mean --sn-input-text-border, --sn-border?)

Re-run with --apply to write these changes.

It reads the token layout out of the installed package's own stylesheets, so it cannot disagree with the version you have, and it reports three things: tokens the library no longer defines, tokens set where they cannot reach the element that declares them, and contract tokens that are missing. Nothing is written until you pass --apply, and even then your values and comments are preserved - a moved token keeps its value, and a rename is only ever suggested, never applied, because picking the replacement is a judgement call. Add --check to fail a build when a theme falls behind.

Elevation and selection

Surfaces that float over the page carry an elevation shadow and no outline: --sn-shadow-overlay for menus, popovers, toasts and every dropdown panel, --sn-shadow-modal for dialogs and drawers, --sn-shadow-sm for cards and accordions. The ramp follows Material's steps, so a dialog always sits above a dropdown. Components that are part of the page rather than over it stay flat: panel, scroll panel, tabs, table, breadcrumb, chip, badge, and every input-based control, which keep the 1 px field border that makes them legible as controls.

Each of those borders is still a token set to none or transparent, so an outlined look is one declaration away: --sn-card-border-color, --sn-dialog-border, --sn-menu-border, --sn-select-panel-border and their siblings. Border widths were left in place, so switching one on shifts nothing.

A selected row, cell or segment is a 16% tint of the accent rather than a fill of it: --sn-selected-bg, --sn-selected-bg-hover and --sn-selected-text. All three derive from --sn-color-primary, so a theme picks them up by setting that one token, and neither the contract nor a per-mode block needs to mention them. Selection outranks hover: a selected row keeps its tint under the pointer.

The glass theme

Glass uses backdrop-filter: blur(24px) and translucent panel backgrounds (rgba(255,255,255,0.08)) over a dark canvas (rgb(10,10,18)). For full visual fidelity, the app-level background should also include the ambient mesh gradient - three blurred radial blobs in red, indigo, and cyan. See the --sn-backdrop-filter and --sn-glass-shadow tokens.

Tailwind integration

Import ashen-ui/styles/tailwind.css in your app's stylesheet after @import "tailwindcss". It maps every public --sn-* token into Tailwind's theme namespace so you get utilities like bg-sn-primary, text-sn-error, rounded-sn-md, and font-sn-ui. The library itself never uses Tailwind - plain CSS consumers simply omit this file.
